    rc.3: a language server, data that moves between threads, and raw assembly¶

    v1.0.0-rc.3 makes Stenopos feel like a language you live in, not just one you compile with. Your editor now understands it, concurrent tasks can hand real data back and forth without copying or races, and — for the rare moments you need it — you can drop all the way down to raw machine instructions.

    As always, everything here was written in Stenopos, compiled by Stenopos, and checked the same way: the compiler builds itself twice and the two results come out byte-for-byte identical.

    Your editor now understands Stenopos¶

    Stenopos ships a language server. Point any editor that speaks LSP — VS Code, Neovim, and most others — at stenopos lsp, and you get:

    • Live error checking. As you type, mistakes get a red underline with the real compiler's message — the exact same check that runs at build time, not a rough imitation. Fix the problem and the underline disappears.
    • Hover a name to see what it is.
    • Jump to definition of a function, struct, or enum.
    • Completion for keywords, built-ins, and the names in your file.

    It's one command — the language server is built into the stenopos binary, nothing extra to install. Setup for Neovim and VS Code is in the docs.

    Passing real data between Hemerodromes¶

    A Hemerodrome is a concurrent unit of work you start with spawn. Until now, the mailbox between Hemerodromes — a channel — could only carry simple numbers. Now it carries real things: text, structs, lists, and maps.

    chan[str] ch = chan()
spawn producer(ch)
str msg = ch.recv()        // a whole string arrives, safely

    The trick is a simple rule: sending gives the value away. When you send something down a channel, the sender no longer owns it — the receiver does. There is never a moment where two Hemerodromes both hold the same piece of memory, so there's no race and nothing gets freed twice. The compiler enforces this for you; if you want to keep a copy, you say so with .clone(). And because sending is a handover, not a copy, it costs the same whether you send three characters or three megabytes.

    Locks learned the same lesson. A mutex[Point] can guard a real struct, and you can change it in place while you hold the lock — no copying it out and back:

    with (p = m.borrow()) {
    p.x = p.x + 1          // changed right where it lives, under the lock
}

    That borrow is fenced in: the compiler won't let the pointer escape the locked section, so you can't accidentally keep using it after the lock is released. There's a read-only version, read_borrow(), for when many readers just want to look.

    Inline assembly¶

    Sometimes you need to say exactly what the machine does. asm { } lets you write raw instructions, with the GCC-style operand syntax for feeding values in and getting them out:

    unsafe {
    asm {
        "addl %1, %0"
        : "=r"(sum)
        : "r"(a), "r"(b)
    }
}

    It's gated behind unsafe, because it is. This is the last piece the green-thread scheduler needed for its hand-written context switch — and it opens the path to running Stenopos with no C runtime underneath at all.

    Smaller and quicker, too¶

    Calls between functions in the same program now go directly to their target instead of through an indirection table, the way a C compiler does it — a little less overhead and a little smaller on disk, for free.

    Getting it¶

    Same as always — grab the compiler, point it at a .sten file, and run it. The full list of changes is in the changelog.

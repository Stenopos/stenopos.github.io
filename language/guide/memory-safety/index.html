    Memory Safety¶

    Stenopos manages memory with NOVA: no garbage collector and no manual free. The compiler inserts every allocation's release at the point the value's owner goes away.

    Freed at the end of scope¶

    func process() -> void {
    str data = "a string on the heap"
    println(data)
    // data is freed here, automatically
}

    Strings, lists and maps free their memory when their owner leaves scope, on every path out: falling off the end, return, break, continue or a throw. The CI runs the whole test corpus under valgrind and accepts no use-after-free, no double free and no leak.

    Sending a local string, list, map or struct on a channel moves it: the receiver owns it now. Using it afterwards is a compile error until it is assigned a new value, on every path: after an if that sent it in one branch, after a loop that sent it and left with break, and in a loop that sends it and goes round again without assigning it:

    func main() -> void {
    chan[str] c = chan()
    str job = "first"
    c.send(job)
    // println(job)       // error: `job` was moved: sent on a channel at line 4
    job = "second"        // a new value: usable again
    c.send(job)
}

    A parameter is sent as a copy (the caller still owns it), and numbers and bool always copy. From rc.8; before, a value used after send read as empty or crashed. Moves at every hand-over (str b = a) come with M6 (ADR-0040).

    Ownership¶

    Every value has exactly one owner.

    Today, handing a value to a new owner copies it: after str b = a, a and b are independent, and changing one never affects the other. This is always safe; the compiler already avoids the copy when a is not used again.

    x.clone() makes an independent deep copy of a string, list, map or struct (from rc.8). It is how a program keeps a value it hands on once handing on moves (ADR-0040): c.send(job.clone()) sends a copy and keeps job.

    Parameters borrow¶

    Passing a struct, list or map to a function doesn't copy it: the parameter borrows the caller's value for the length of the call. A function that changes its parameter changes the caller's value, just as a method changes this:

    struct Account {
    str owner
    float64 balance
}

func transfer(Account from, Account to, float64 amount) -> void {
    from.balance = from.balance - amount
    to.balance = to.balance + amount
}

func main() -> void {
    Account a = Account { owner: "ana", balance: 100.0 }
    Account b = Account { owner: "ben", balance: 0.0 }
    transfer(a, b, 30.0)
    println("{a.balance} {b.balance}")   // 70 30
}

    Assigning to the parameter itself (from = Account { ... }) only rebinds the name inside the function; the caller's value is untouched. Returning a parameter returns a copy.

    A value passed to a parameter the function changes can't also appear in another argument of the same call: both parameters would name the same value, and a push through one could move the memory the other is reading. The compiler works out which parameters each function changes (following the calls it makes), and rejects the call:

    transfer(a, a, 30.0)
// error: `a` is passed to `transfer` twice, and `transfer` changes its
// parameter `from`, so two parameters would borrow the same value; pass
// a copy instead: `Account a_copy = a`

    The same goes for a value and a field inside it (f(a, a.items)) and for a method's receiver (a.merge(a)). Strings and numbers are passed by value, so they never conflict. spawn gives the new Hemerodrome its own copy of each struct argument, because it can outlive the caller.

    Coming in 1.0: moves (ADR-0040)

    Values that own heap memory (str, List, HashMap, and structs that contain them) will move instead: after str b = a, a can no longer be used, and the compiler reports it if you try. Copying becomes explicit with .clone(). Numbers, bool and structs of plain data still copy implicitly. A parameter keeps borrowing (above) unless the function keeps the value, by storing or returning it: then the parameter consumes it, with no copy. The compiler infers this without any annotation, as it already infers which parameters are changed. spawn takes its arguments instead of copying them, and a clone of a @sensitive or secret value stays protected.

    str a = "hello"
str b = a          // a moves into b
println(a)         // error: use of moved value `a`
str c = b.clone()  // an explicit, independent copy

    Moves make transfers free (no hidden copies), let messages and channels hand data over without copying, and let capabilities be values that can't be duplicated.

    Raw pointers¶

    For talking to C, raw pointers exist, confined to unsafe blocks:

    func main() -> void {
    int32 x = 41
    unsafe {
        ptr[int32] p = &x
        *p = *p + 1
    }
    println("{x}")     // 42
}

    Everything that makes or uses a pointer needs unsafe (ADR-0041): taking an address (&x), reading or writing through one (*p), casting to or from one, comparing two, and calling a C function. So the unsafe blocks are the complete list of places to audit.

    A ptr[T] knows its T: *p reads and writes a T, and a ptr[int64] isn't a ptr[int32]. ptr[void] is C's void *: any pointer converts to it, and it converts back only by a cast. C's narrow integers (uint8, int8, uint16, int16) have no Stenopos type of their own: through a ptr[uint8], *p reads an int32 and a store keeps the low byte. &s of a struct is the address of its fields, which is what C's struct T * means.

    extern "C" {
    func malloc(uint64 size) -> ptr[void]
    func free(ptr[void] p) -> void
}

func main() -> void {
    unsafe {
        ptr[int64] p = cast[ptr[int64]](malloc(8))     // ptr[void] -> ptr[int64]
        if (p != cast[ptr[int64]](0)) {                 // null is cast[ptr[T]](0)
            *p = 5000000000
            println("{*p} at {cast[uint64](p)}")       // an address is a uint64
            free(p)
        }
    }
}

    A device register is memory that acts: writing a UART's data register sends a byte, and its status register changes on its own. volatile_read(p) and volatile_write(p, v) are *p and *p = v that the compiler performs exactly as written, once each and in order, even when nothing reads the value back (which would otherwise let the optimizer drop the write):

    func put(uint8 c) -> void {
    unsafe {
        ptr[uint8] status = cast[ptr[uint8]](cast[uint64](0x10000005))
        while ((volatile_read(status) & 32) == 0) {      // wait until it can send
        }
        volatile_write(cast[ptr[uint8]](cast[uint64](0x10000000)), c)
    }
}

    Volatile keeps the compiler's order, not the processor's: for that, see fences.

    From rc.8; in rc.7 and earlier &x was allowed outside unsafe, *p read an int32 whatever T was, and there was no volatile access. Reading a whole struct through a pointer (*p on a ptr[S]) isn't supported yet: pass the pointer on to C.

    Device registers¶

    Raw addresses, widths and casts repeated through every driver are where a wrong offset hides. A register block describes a device's registers once, by offset, width and access (ADR-0058):

    @registers
struct Ns16550 {
    @at(0x0) write uint8 thr      // transmit holding: a byte written is sent
    @at(0x1) uint8 ier            // interrupt enable: read and written
    @at(0x5) read uint8 lsr       // line status: bit 5, ready for a byte
}

func uart() -> Ns16550 {
    unsafe {
        return registers_at[Ns16550](0x10000000)   // the one unsafe fact
    }
}

func put(Ns16550 u, uint8 c) -> void {
    while ((u.lsr & 32) == 0) {          // one volatile 8-bit read per test
    }
    u.thr = c                            // one volatile 8-bit write
}
    • @at(offset) places each register, in bytes from the block's address. A register is uint8, uint16, uint32 or uint64; registers may leave gaps, but may not overlap and must be aligned to their width.
    • read or write restricts a register; no keyword means both. Reading a write register or writing a read one is a compile error naming it, and so is += on a write register (it would read first).
    • Every access is exactly one volatile access of the register's width, as volatile_read and volatile_write are. A read-modify-write is written out (u.ier = u.ier + 1): two accesses, both visible.
    • registers_at[T](address) binds a block to an address, inside unsafe: nothing can check that the device is there. After that, accesses need no unsafe. A block's value is its address: passing it, returning it, or holding it in a struct copies the address, never the device.

    In a firmware project the addresses aren't in the source at all: Tagma.toml's [devices] binds each block, and main receives the board (func main(Board board), then board.uart0), with no unsafe; see Firmware.

    From rc.8. Still to come: making a bound block move-only, so one driver owns a device (with move checking, M6); bit fields by name; and register arrays.

    Interrupts, statics and fences¶

    A timer's interrupt arrives between any two instructions; the code it runs needs somewhere to keep what it counts, and a driver handing a buffer to a device needs memory to settle in order. Three things cover it (ADR-0059).

    Statics. A static is a variable that lives for the whole program, declared at the top of a module: an integer, bool or float64, with a constant first value. Reading or writing one is unsafe, since an interrupt can change it between two instructions and nothing makes that safe until M6's atomics. Every access is volatile, so a loop waiting for an interrupt reads it each time round:

    static uint64 ticks = 0

func tick() -> void {
    unsafe {
        ticks += 1
    }
}

func main() -> void {
    tick()
    tick()
    unsafe {
        println("{ticks} ticks")      // 2 ticks
    }
}

    A local of the same name hides a static. A pub static can be imported from another module like a function.

    Interrupt handlers. @interrupt marks a function the hardware runs: no result, and no parameters or, as main does, the Board, so a timer's handler can re-arm its timer. It is ordinary, checked Stenopos. The compiler writes its entry, which saves the registers the handler may change (the FP/SIMD state too when the board uses its FPU: see float64 on a board), calls it, restores them and returns from the exception (mret, eret, iretq). interrupt_entry(f) is the entry's address, a uint64, for the board's code to install: in mtvec on RISC-V, as a branch in the vector table on ARM64, in an IDT gate on x86-64. On RISC-V (QEMU's virt board):

    @interrupt
func on_timer(Board board) -> void {
    unsafe {
        ticks += 1
    }
    arm(board.clint, 100000)         // the next one in 10 ms
}

func take_ticks(Board board) -> void {
    uint64 entry = interrupt_entry(on_timer)
    arm(board.clint, 100000)
    unsafe {
        asm {
            "csrw mtvec, %0"         // interrupts run on_timer's entry
            "li t0, 0x80"
            "csrs mie, t0"           // the timer's interrupt
            "csrsi mstatus, 0x8"     // interrupts on
            :
            : "r"(entry)
            : "t0"
        }
    }
}

    @interrupt is for freestanding programs. The interrupt controller (acknowledging, priorities, nesting) is the program's, written with register blocks; stenopos-os's pathfinder takes timer interrupts this way on RISC-V, ARM64 (the GIC) and x86-64 (the local APIC). An x86-64 board build leaves out the red zone, since an interrupt pushes its frame just below the stack pointer.

    Fences. memory_fence() makes every memory access before it, to memory or a device, complete before any after it begins, as the whole system sees it (fence iorw, iorw on RISC-V, dsb sy on ARM64, mfence on x86-64). Volatile access keeps the compiler's order; a fence keeps the processor's and the bus's, for instance between filling a buffer and telling a device to read it. It is safe code. There is one fence, the strongest; lighter ones can come when a measurement asks for them.

    From rc.8. Still to come with M6: atomics, so a counter shared with a handler needs no unsafe.

    Calling C¶

    extern "C" {
    func abs(int32 n) -> int32
    func labs(int64 n) -> int64
}

func main() -> void {
    unsafe {
        println("{abs(0 - 7)} {labs(0 - 9)}")
    }
}

    From rc.8 a C function can take and return any of these, mixed freely, and each call's arguments are checked against them like any other call's:

    Stenopos C
    int32, uint32 int, unsigned
    int64, uint64 long, size_t (and other 64-bit integers)
    bool bool (_Bool, one byte)
    float64 double
    ptr[T] T * (a struct with @repr("C"), or a scalar)
    str (parameters) const char *: a NUL-terminated copy, valid for the call 
    extern "C" {
    func strlen(str s) -> uint64
    func snprintf(ptr[uint8] buf, uint64 size, str fmt, ...) -> int32
}

    A str with a NUL byte inside stops the program rather than reaching C: C would read only up to the NUL, and a path or a name cut short is a bug at best. A C function can't return str (who frees C's string is up to C): return ptr[uint8] and copy it. After ..., a variadic function's arguments travel as C's default promotions do. Integer literals, and arithmetic on them (0 - 7), take the parameter's type; an int32 variable does not become an int64 without cast[int64]().

    Structs by value. A @repr("C") struct whose fields are scalars, pointers or enums can be a C function's parameter or result. How C passes structs differs on every architecture, so the call goes through a small C wrapper that the compiler writes and the target's own C compiler builds:

    @repr("C")
struct DivT {
    int32 quot
    int32 rem
}

extern "C" func div(int32 num, int32 den) -> DivT

    Callbacks. A parameter of a function type takes a named top-level function, which C calls through a plain function pointer:

    extern "C" func qsort(ptr[int32] base, uint64 n, uint64 size, fn(ptr[int32], ptr[int32]) -> int32 compare) -> void

    Its parameters and result must be ones C can pass (integers, float64, bool and pointers), and a lambda isn't accepted: its captured variables have no C form. An error thrown out of a callback can't unwind through C's frames, so it ends the program (exit status 70) with its message.

    Limits today

    rc.7 and earlier: parameters and result all int32, or all int64, and none of the above. Still to come: a struct whose field is another struct is stored as a pointer to it, not inline as C stores it, so such a struct can't be passed by value yet, and reading one through a pointer isn't C's layout.

    No null dereferences¶

    Nullable values (T?) must be checked before use; the compiler narrows the type after the check (see Variables and Types). Raw pointers will follow the same rule as ptr[T]?.

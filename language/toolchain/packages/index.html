    Packages and the registry¶

    In progress

    New in rc.6

    Everything on this page ships in v1.0.0-rc.6. The registry's first package, stenopos/dotenv, follows shortly; until then the index is empty. Publishing is open to the Stenopos organization first.

    Using packages¶

    $ tagma add stenopos/dotenv
       Added dotenv = stenopos/dotenv 1.0.0 (granted File)

    tagma add picks the newest version (or the one you name, stenopos/dotenv@1.0.0), writes one line to Tagma.toml, and grants the package the capabilities that it and its dependencies use:

    [dependencies]
dotenv = { package = "stenopos/dotenv", version = "1.0.0", allow = ["File"] }
    • Names are namespaced (stenopos/json), so nobody can squat a short name and you can see who owns a package. You import a package by the name on the left (import dotenv.{load}); tagma add --as env picks another.
    • version = "1.2" means "at least 1.2.0" in the 1.x line.
    • --allow File,Network (or --allow none) grants exactly that instead; if it is not enough for the package, add says which capability is missing and changes nothing.
    • After every edit tagma selects versions, fetches each package and checks its hash and grants. If anything fails, Tagma.toml, Tagma.lock and vendor/ are left exactly as they were.
    • The rest of Tagma.toml (comments, order) is kept as you wrote it.
    $ tagma update            # every dependency, or: tagma update dotenv
     Updated dotenv: stenopos/dotenv 1.0.0 -> 1.1.0
$ tagma remove dotenv
     Removed dotenv (stenopos/dotenv)

    tagma update moves each requirement to the newest version of its major version. A new major version is a different package: update mentions it, and tagma add stenopos/dotenv@2.0.0 moves to it. A new version that needs a capability you haven't granted is refused, naming it; raise the grant yourself if you trust it.

    Dependencies only get the powers you grant¶

    Every package's capabilities (File, Network, Process, Memory, System) are computed when it is published. In Tagma.toml you grant each dependency the capabilities it may use:

    [dependencies]
json = { package = "stenopos/json", version = "1.2", allow = [] }
files = { package = "stenopos/files", version = "1.0", allow = ["File"] }

    If a new version of a JSON library suddenly wants Network, your build fails and names the package and the capability, instead of quietly giving it network access.

    • Grants pass down, never up. A package can give its own dependencies only what it was given: what a package may use is what every grant on every path to it allows (your grant, then each package's grant to its dependencies in its own Tagma.toml).
    • The compiler enforces it on the code. tagma checks the capabilities the registry recorded, and the compiler holds each package's source to the same limit: a function in it may declare only granted capabilities, so a package that misrecorded them still can't use more.
    • unsafe needs Memory; extern "C" and inline asm need System. Raw memory and foreign code could do anything, so granting System means trusting the package with everything.
    • Your own code and path dependencies are not limited.

    Predictable versions¶

    tagma uses minimal version selection: for each package it takes the highest of the minimum versions anything asks for, and never a newer version that nobody asked for. Versions only move when you run tagma update or tagma add. Tagma.lock records exactly what was chosen.

    Precisely: a requirement "1.2" selects the lowest published 1.x version that is at least 1.2.0, and that version's own requirements are followed in turn. For each package and major version, the build uses the highest version reached. Retracted versions are skipped, unless Tagma.lock already names one. tagma fetch (and add, update, or any build whose lock no longer matches Tagma.toml) writes the result to Tagma.lock:

    version = 1

[[package]]
name = "stenopos/json"
version = "1.2.0"
repository = "https://github.com/Stenopos/json"
commit = "2222222222222222222222222222222222222222"
hash = "sha256:…"
caps = ["File"]
dependencies = ["stenopos/text 1.0.3"]

    Each entry is a selected version with the commit and content hash its source must match, the capabilities its code uses, and the exact versions of its own dependencies (caps here records what each package uses; allow in Tagma.toml is what you grant). With --locked, a command fails instead of changing the lock, for CI.

    Integrity and trust¶

    • The registry is a signed index (a git repository) recording each version's source commit and a hash of its files. It does not host code.
    • tagma checks that hash before compiling anything, and Tagma.lock records it, so every later build verifies against it.
    • The index carries a signed snapshot with a seven-day expiry, so an old or frozen copy of the index is detected.
    • Every version is signed by its publisher, and the registry's root key is kept offline.
    • The exact format is FORMAT.md in the registry repository, and tagma registry check checks a checkout against it, every signature included. The registry's CI runs it on every change.

    Fetching and checking¶

    tagma build (and run, check, test) fetches what a project needs. If Tagma.lock still satisfies Tagma.toml, it is used as it is and the index isn't needed at all; otherwise tagma updates its copy of the index, selects versions and rewrites the lock first (tagma fetch does just that).

    • The index is a clone of the registry in ~/.cache/stenopos/registry. It is used only after every signature checks out against the root key built into tagma, and only with a snapshot that hasn't expired and isn't older than one already seen. Anything else is refused, and the previous copy is kept.
    • A package is fetched by its commit (from GitHub, then its mirror) into ~/.cache/stenopos/src/<namespace>/<name>/<version>, and used only if its files hash to the content hash in Tagma.lock. That is checked again on every build, so a file changed in the cache is noticed and fetched afresh.
    • --offline uses only the cache; --locked fails rather than change Tagma.lock (for CI).
    • STENOPOS_CACHE moves the cache. STENOPOS_REGISTRY_URL and STENOPOS_REGISTRY_ROOT (a file with the root public key) point tagma at another registry, such as a private one.

    Vendoring¶

    $ tagma vendor
    Vendored 3 package(s) into vendor/ (commit it; builds use it and check every hash)

    tagma vendor copies every locked package into vendor/<namespace>/<name>/<version>. A project with a vendor/ directory builds from it alone, with no network and no cache, and still checks each package against the content hash in Tagma.lock, so an edited vendored file is refused. add, remove and update keep vendor/ in step.

    Publishing¶

    A package is a library (src/lib.sten) with a namespace and a repository in Tagma.toml:

    [package]
name = "dotenv"
namespace = "stenopos"
version = "1.0.0"
edition = "2026"
repository = "https://github.com/Stenopos/dotenv"

    To release a version, raise version, commit, and tag the commit v<version>. The package's CI then runs tagma publish, which:

    1. takes the files of the tagged commit (uncommitted changes are never part of a version) and computes their content hash;
    2. tests the package, resolving its dependencies afresh;
    3. finds the capabilities its code uses (tagma caps);
    4. writes the version entry into a checkout of the registry, signs it with the publisher key, checks the whole checkout (tagma registry check), and commits it.

    The registry's CI then re-derives the entry from the source (tagma registry verify: the files at the commit must hash to the recorded hash, and the manifest, dependencies and capabilities must match), re-signs the snapshot and publishes the index. tagma publish --dry-run --registry <checkout> shows the entry and the statement its signature covers without writing anything.

    A published package depends only on registry packages (not paths), and a version can never be changed or removed, only retracted. CI acts only on tags signed by a Stenopos release signer, at the commit being built: write access to a package's repository is not enough to publish.

    Retracting a version¶

    A broken version is retracted by pushing a signed tag retract/<version> (git tag -s retract/1.2.0); CI runs tagma retract, which signs the retraction and commits it to the registry. A retracted version is never chosen for a new resolution (add, update), but a project whose Tagma.lock already names it keeps building.

    When a publisher key is compromised¶

    The registry's root key revokes it from a date. Every version that key signed on or after that date is revoked: unlike a retracted version, it is refused even where Tagma.lock names it. Once your copy of the index updates (tagma fetch, add, update), a build with a revoked version locked stops and names it; tagma fetch moves you to a version that isn't revoked. Because the registry only accepts entries dated the day they are published, a stolen key can't slip in a version dated before its revocation.

    What a package's code uses¶

    $ tagma caps
caps = ["File"]
$ tagma check --allow none
error[E0400]: this function's `@cap(File)` needs the File capability, but this package is granted no capabilities

    tagma check --allow <A,B> holds every file of the package to those capabilities, exactly as a project's grant would. tagma caps finds the smallest set the package compiles within: what its registry entry records.

    Commands¶

    Command What it does
    tagma add <ns/name>[@<version>] [--as <name>] [--allow <A,B>\|none] Depend on a package, granting what it uses
    tagma remove <name>... Stop depending on a package (by import name or package)
    tagma update [<name>...] Move to the newest version of each major version
    tagma fetch Update the index, select versions and fetch every package
    tagma vendor Copy the packages into vendor/ for builds with no network
    tagma caps The capabilities the package's own code uses
    tagma check --allow <A,B>\|none Check that the package's own code needs only those capabilities
    tagma publish --registry <checkout> --key <file> --publisher <name> [--tag <tag>] [--dry-run] Write and sign this commit's registry entry (CI runs it)
    tagma retract <version> --registry <checkout> --key <file> --publisher <name> Retract a published version (CI runs it on a retract/<version> tag)
    tagma registry check [<dir>] [--previous <dir>] Check a registry checkout: format, signatures, append-only history
    tagma registry verify [<dir>] [--previous <dir>] Re-derive each new entry from its source
    --locked Fail if Tagma.lock would change (for CI)
    --offline Use only the cache and vendor/; never the network
    --registry <checkout> Use a local registry checkout instead of the published index (checked the same way, except for the snapshot's expiry)

    The standard library is not a registry package: it ships with Syntagma.

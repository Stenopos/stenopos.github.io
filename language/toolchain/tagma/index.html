    Projects with tagma¶

    In progress

    Commands¶

    Command What it does
    tagma new <name> Create <name>/ with Tagma.toml, src/main.sten and .gitignore
    tagma build [--release] [--target <arch>] Compile to target/draft/<name> (or target/release/<name>)
    tagma run [--release] Build, then run
    tagma check [--allow <A,B>\|none] Type-check without linking (--allow: the project's own code may use only those capabilities)
    tagma board A firmware project's memory, layout and devices, with each one's Tagma.toml line and the code that uses each device (from rc.8; see Firmware)
    tagma test Run every @test function in src/ and tests/
    tagma fmt [--check] Format the sources
    tagma lint Lint the sources
    tagma doc Write the public API to target/doc/<name>.md
    tagma clean Remove target/
    tagma add <ns/name>[@<version>] Depend on a registry package (Packages and the registry)
    tagma remove <name> Stop depending on one
    tagma update [<name>] Move dependencies to their newest versions
    tagma fetch [--locked] [--offline] Update the registry index, select versions (Tagma.lock), and fetch and check every package
    tagma vendor Copy the packages into vendor/ for builds with no network
    tagma caps The capabilities the project's own code uses
    tagma publish Publish this commit as a registry version (CI runs it)
    tagma retract <version> Retract a published version (CI runs it)
    tagma registry check [<dir>] Check a checkout of the package registry: its format and every signature (Packages and the registry)
    tagma completions bash\|zsh\|fish Print the script that makes Tab complete tagma (from rc.8; see Tab completion)

    --feature NAME turns on @cfg(feature == "NAME") code.

    Tab completion¶

    New in rc.8

    Not in rc.7 or earlier releases.

    Tab completes tagma and stenopos: commands and flags, --target and --allow values, .sten files where a source file goes, the error codes after stenopos explain, package names after tagma add (from the registry index tagma keeps; completion never uses the network), and your dependencies after tagma remove and tagma update.

    The installer sets it up for bash, zsh and fish, under the install prefix's share/ directory, where each shell looks. To load it by hand (the same for stenopos):

    source <(tagma completions bash)                               # in ~/.bashrc
source <(tagma completions zsh)                                # in ~/.zshrc, after compinit
tagma completions fish > ~/.config/fish/completions/tagma.fish

    Tagma.toml¶

    [package]
name = "hello"
version = "0.1.0"
edition = "2026"

[dependencies]
util = { path = "../util" }
    • name: letters, digits, - and _, starting with a letter.
    • version: the project's own semantic version.
    • edition: the language edition the project is written in.
    • namespace, repository: only for a package published to the registry: its namespace (stenopos) and its git repository's https:// URL.

    A program's entry point is src/main.sten; a library's is src/lib.sten. check, test and doc work on both; build and run need a src/main.sten.

    Where tagma's messages go¶

    tagma's progress lines (Compiling, Finished, Running, Added...) go to stderr, so a program's output under tagma run is the only thing on stdout: tagma run > out.txt holds just the program's. To send them elsewhere, or keep a log, add an [output] table to Tagma.toml:

    [output]
status = "stdout"            # "stderr" (the default), "stdout", or "none"
log = "logs/build.log"       # also append everything tagma prints here

    The log gets each run's command line ($ tagma build) and then everything written to stderr while it runs: tagma's messages, the compiler's diagnostics in full, a failing llc or cc. Its directory is made if needed. The program tagma run starts keeps its own output; for a log of what a program does, use std.logging.

    For one run, the command line overrides the file: --status stdout|stderr|none, -q or --quiet (the same as --status none), and --log <file>. Errors always reach stderr, whatever status says, so a failure is never hidden.

    Build profiles¶

    tagma build makes a draft build: fast to compile and easy to debug. tagma build --release makes an optimized, stripped build that reads like a generic C binary. Every build is hardened: position-independent, full RELRO, a non-executable stack and stack protection.

    Stack size¶

    A program's main thread gets the system's stack, as a C program does: usually 8 MiB (ulimit -s shows it). A program that recurses deeply (a parser of deeply nested input, a recursive search) can ask for more:

    [build]
stack = "256MiB"             # a number of bytes, or with KiB, MiB or GiB

    or stenopos build --stack 256MiB for a single file. The program then raises its limit and starts itself again before main, once; a program that doesn't ask starts once and pays nothing. Running out of stack stops the program with stack overflow and this advice, not a bare "Segmentation fault". Programs that tagma or stenopos run start get the stack your shell gave them, never the toolchain's own (1 GiB), so what passes under tagma run behaves the same on its own.

    On Linux a stack is virtual memory; the kernel decides which physical memory backs it, and only the pages a program touches use any.

    Firmware¶

    A project that runs on a board with no operating system (a boot loader, a device's firmware, an OS kernel) describes the board in Tagma.toml. tagma builds it freestanding, writes its linker script, and hands main the board's devices. From rc.8 (ADR-0057, ADR-0058):

    [target]
kind = "firmware"                 # no OS, no C library
arch = "riscv64"                  # riscv64, aarch64 or x86_64

[memory]
ram = { origin = 0x8000_0000, size = "128MiB", kind = "code" }

[layout]
code  = "ram"                     # code and constants
data  = "ram"                     # statics
stack = { region = "ram", size = "64KiB" }

[devices]
uart0 = { type = "uart.Ns16550", at = 0x1000_0000 }
power = { type = "sifive.SifiveTest", at = 0x10_0000 }
    • [memory] names the board's regions: each has an origin, a size (in bytes, or "64KiB", "128MiB", "1GiB") and a kind: code (executable RAM), data or rom (read-only, executable). Regions may not overlap.
    • [layout] says which region holds code, data and the stack, and the stack's size. With a single region it may be left out.
    • The linker script is generated from the two, into target/<profile>/link.ld: nobody writes one. A region that overflows fails the build, naming it, and every build reports each region's use:
       Compiling pathfinder v0.1.0 (release)
      Memory ram      64.5 KiB of 128 MiB (0.0%)
    Finished target/release/pathfinder
    • [devices] binds each device to an address: its type is a register block, named with the module it is declared in (uart.Ns16550 for src/uart.sten). A device may not sit inside a memory region or overlap another device.

    The devices reach the program as a value. tagma writes target/board.sten on every build (a real file, to read; not to edit), with a Board that has one field per device, and main receives it:

    import board.{Board}
import uart.{Ns16550, put}

func main(Board board) -> void {
    put(board.uart0, 65)          // board.uart0: the UART at 0x1000_0000
}

    Using board.uart0 needs no unsafe: the address is Tagma.toml's, reviewed with the board, and each device is a constant address, so the board costs nothing at run time. Only tagma's generated file may declare a @board; a program that binds a device itself does so with registers_at inside unsafe. src/board.sten is refused, since board is the generated module's name.

    tagma board shows it all, with where each part comes from:

    Board: firmware for riscv64 (Tagma.toml:7)

Memory
  ram        0x80000000     128 MiB    code   Tagma.toml:12

Layout
  code    ram
  data    ram
  stack   ram, 64 KiB

Devices
  uart0      uart.Ns16550         0x10000000     Tagma.toml:20
      used at src/main.sten:22: put(board.uart0, 65)

    Every problem names its line:

    Tagma.toml:20: device `uart0` at 0x80001000 is inside region `ram` (Tagma.toml:12)
error[E0300]: `board.uart1` doesn't exist: Tagma.toml declares uart0, power

    The program brings its own start-up code (a @naked _start in section .text.start, which the linker script places first), as the pathfinder in stenopos-os shows for each architecture. @cfg(target_os == "none") selects code for a freestanding build.

    Still to come (ADR-0057): placing functions and statics in a region (@place), a freestanding runtime so strings and println work, proven stack bounds, and boards as packages.

    Dependencies¶

    Today a dependency is a local path to another project. Its src/ directory becomes an import root:

    util/src/lib.sten        module util ... pub func greet(str who) -> str
hello/src/main.sten      import util.{greet}

    Registry packages are added with tagma add; see Packages and the registry.

    Tests¶

    // tests/math.sten
@test
func adds() -> void {
    if (1 + 1 != 2) {
        fail("math is broken")
    }
}

    tagma test

    A test in tests/ imports the project's own modules (import dotenv.{parse} for a library whose src/lib.sten is module dotenv). A test function that needs a capability declares it, like any function:

    @cap(File)
@test
func reads_config() -> void {
    if (read_file("Tagma.toml") == "") {
        fail("no manifest")
    }
}

    Single files¶

    stenopos keeps its single-file commands (stenopos run file.sten, build, check, fmt, lint, doc, test). Inside a project, it points you to tagma instead.

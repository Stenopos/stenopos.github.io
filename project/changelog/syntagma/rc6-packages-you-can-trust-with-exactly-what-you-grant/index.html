    rc.6: packages you can trust with exactly what you grant¶

    v1.0.0-rc.6 brings the package registry. A project can depend on published packages, and each one gets only the capabilities you grant it, enforced by the compiler on its code.

    Using packages¶

    The first package, stenopos/dotenv, is written and tested, and will be published to the registry shortly after this release. Adding it will look like this:

    $ tagma add stenopos/dotenv
       Added dotenv = stenopos/dotenv 1.0.0 (granted File)

    tagma add writes one line to Tagma.toml and grants the package what it and its dependencies use:

    [dependencies]
dotenv = { package = "stenopos/dotenv", version = "1.0.0", allow = ["File"] }

    Take File away and the build stops, naming the package and the capability. A dependency can only pass on to its own dependencies what it was granted, and the compiler holds every package's source to its limit: unsafe needs Memory, extern and asm need System.

    tagma update moves to the newest version of each major version, tagma remove drops a dependency, and tagma vendor copies everything into vendor/ for builds with no network. Versions are chosen by minimal version selection and recorded in Tagma.lock with each package's commit and content hash; every build checks the files against it.

    See Packages and the registry.

    A registry with no server¶

    The registry is a signed git index that records where each version's source lives and a hash of its files:

    • The root key, kept offline, approves the keys that sign; a snapshot signed daily expires after seven days, so a frozen or replayed index is refused.
    • Each version is published by CI from a signed tag: CI tests it, finds the capabilities its code uses (tagma caps), signs the entry, and the registry's own CI re-derives the entry from the source before accepting it.
    • A broken version can be retracted; a compromised publisher key can be revoked, which revokes what it signed from then on, even from existing lock files.

    Also in rc.6¶

    • Language: function types over any type (fn(List[int32]) -> int32), named functions as values, ordering for str, a lazy and chainable ??, struct parameters that borrow, and str_from_byte (std builds UTF-8 and any bytes on it).
    • Memory: every example, course program and test suite now runs under valgrind in CI, and so does the toolchain itself. Leaks found that way are fixed: discard, clear(), pop() of a struct, and temporaries passed to calls.
    • std: std.toml reads every TOML escape, rejects what TOML forbids, and is fuzzed against Python's tomllib on every build.

    Performance¶

    Every release from now on shows how it compares with C, measured by CI on the tagged commit. Since rc.5:

    • Strings are built in one allocation. A chain of + or an interpolation sums its parts' lengths and copies each part once, where each + used to copy the whole string so far; integers are formatted without snprintf. The string-heavy benchmarks (strings, map, structs) run 44–56% fewer instructions.
    • Overflow checks cost less. Checked arithmetic no longer makes every call of a function save registers it only needs on some paths: recursive fib runs 20% fewer instructions.
    • Smaller binaries. Release builds drop the code a program never calls, such as the copy and drop helpers for struct types it doesn't copy.
    • Faster builds. The compiler's own work on a small build is down by up to 41%: it no longer starts extra processes to check which LLVM it is using, and release builds pass LLVM bitcode instead of text.
    • Loops don't grow the stack. A loop that built strings used a new stack slot on every iteration; a long one could overflow a task's stack.

    Each program is written twice, in Stenopos and in C, and both must print the same output. Stenopos builds with stenopos build --release, C with cc -O2 -s. Each cell shows the Stenopos number, then Stenopos ÷ C: below 1× means Stenopos uses less. Instruction counts come from valgrind, so they are exact and repeat run to run. Build counts include the whole toolchain (LLVM, the C compiler, the linker).
